# Архітектура обробки тексту

## Глобальний конвеєр: 7 етапів трансформації тексту в 3D-музей

---

### Етап 1: Поглинання та нарізка (Ingestion Layer)

Процес стартує, коли користувач завантажує наукові праці (PDF) та вводить свої нотатки у форму на сайті.

- **Що відбувається:** Модуль `reader.py` витягує сирий текст із кожного PDF і текстового поля **окремо**. Межі файлів зберігаються — кожен файл чанкується незалежно, щоб текст кінця одного джерела не змішувався з текстом початку іншого.

- **Результат:** Текст нарізається на порції (чанки) по ~500 слів (не 1000 — для 8B-моделей безпечніший розмір) із перекриттям ~50 слів між сусідніми чанками. Кожен чанк зберігає метадані: `{file_id, chunk_index, text}`.

> **Виправлення:** ~~"Фізичні межі файлів стираються"~~ — це баг. Якщо зшити всі файли в один потік, подія з кінця статті A отримає дату з початку статті B. Чанкування тільки всередині файлу.

---

### Етап 2: Атомарна екстракція подій (Перший прохід ШІ)

Перетворює сирий текст на первинну таблицю фактів.

- **Що відбувається:** Кожен чанк подається в Ollama з суворим промптом у форматі JSON. Модель витягує конкретні події та для кожної створює картку:

  ```json
  {
    "event": "Що відбулося (1–2 речення)",
    "date": "Рік або null",
    "date_confidence": "explicit | null",
    "source_file_id": "назва файлу",
    "chunk_index": 5
  }
  ```

- **Важливо для 8B-моделей:** Промпт містить явну інструкцію `"якщо дата не вказана в цьому тексті — пиши null, не вигадуй"`. Поле `date_confidence: "explicit"` заповнюється тільки коли рік є в тексті буквально.

- **Результат:** Масив карток, частина з `date: null`.

---

### Етап 3: Пошук дат для null-подій

Система намагається встановити дату для подій із `date: null`, але **не через LLM**.

- **Що відбувається (детерміністичний алгоритм, без ШІ):**
  1. Python будує список усіх чанків файлу, впорядкований за `chunk_index`.
  2. Для кожної null-події знаходить найближчий **лівий** чанк того самого файлу, де є хоч одна датована подія, і найближчий **правий**.
  3. Якщо ліва і права дати збігаються → присвоюємо цю дату, `date_confidence: "inferred_certain"`.
  4. Якщо дати різні → присвоюємо проміжок `"між X і Y"`, `date_confidence: "inferred_range"`.
  5. Якщо датованих сусідів немає взагалі у файлі → `date: "unknown"`, `date_confidence: "unknown"`.

- **Чому не LLM для цього кроку:** 8B-модель, отримавши сусідній текст з питанням "яка тут дата?", галюцинує впевнено і часто. Детерміністичний Python-алгоритм на основі вже знайдених дат надійніший.

> **Виправлення:** ~~"Хвильове розширення через Ollama"~~ замінено на Python-алгоритм за вже витягнутими датами з Етапу 2. LLM більше не залучається для датування.

---

### Етап 3.5: Дедуплікація (новий етап)

Перед розкладанням по роках — видалення дублікатів.

- **Що відбувається:** Одна й та сама подія може бути описана в трьох різних завантажених статтях. Python порівнює картки через sentence-transformers (модель `paraphrase-multilingual-MiniLM`) і видаляє ті, що мають косинусну схожість > 0.92. З групи дублікатів залишається картка з найвищим `date_confidence`.

- **Результат:** Чистий масив унікальних подій.

---

### Етап 4: Хронологічний розподіл та тематична кластеризація

Python розкладає події по "кошиках" років. Після цього аналізує щільність кожного року.

**Звичайний рік (до 25 подій):** одразу передається на Етап 5 із `layout: "linear"`.

**Аномальний рік (більше 25 подій):** запускається тематична кластеризація — **без LLM**:

1. **Ембединги:** Python генерує вектор для кожної події через `sentence-transformers` (та сама модель, що й у дедуплікації — безкоштовно, локально, швидко).

2. **Кластеризація:** `HDBSCAN` з `min_cluster_size=5` автоматично знаходить природні тематичні групи. Події, що не увійшли до жодного кластеру, потрапляють у групу "Різне".

3. **Назва теми:** Для кожного кластеру Python знаходить подію, чий вектор найближчий до центроїду кластеру, і бере перші 5 слів її тексту як робочу назву теми. Потім **одним** коротким запитом до Ollama просить придумати людську назву для цього одного представника (не для всієї пачки).

4. **Запобіжник переповнення:** Якщо кластер містить більше 25 подій, HDBSCAN запускається рекурсивно лише на цьому кластері з меншим `min_cluster_size=3`.

> **Виправлення:** ~~"LLM вигадує назви тем для сліпих пачок"~~ — для 8B-моделі це нестабільно: різні пачки дадуть несумісні назви, а їх "склеювання через ШІ" — ще одне джерело галюцинацій. Замінено на ембединги + HDBSCAN (детерміністично) + одиночний LLM-запит тільки для генерації людської назви.

---

### Етап 5: Локальне впорядкування всередині бакетів (Фінальний прохід ШІ)

Кожен тематичний бакет — суверенна, закрита екосистема. LLM працює тільки тут.

- **Що відбувається:** Ollama отримує один бакет (не більше 15 подій) і два завдання в одному промпті:
  1. Розставити події за причиново-наслідковим зв'язком (повернути впорядкований масив індексів).
  2. Написати один абзац-опис цієї підтеми.

- **Захист від перевантаження 8B-моделі:** Промпт не просить "розставити" у вільній формі — він дає пронумерований список і просить повернути `{"order": [3,1,4,2,...], "description": "..."}`. Структурований JSON-вивід різко знижує частоту галюцинацій у малих моделей.

- **Результат:** Кожен бакет — відсортований, із описом, закритий.

---

### Етап 6: Формування JSON для 3D-музею

Python збирає готові бакети в ієрархічну структуру для Three.js.

- Каркас музею будується **строго хронологічно** (Кімната 1918 → 1919 → 1920). Події з `date_confidence: "inferred_range"` або `"unknown"` рендеряться напівпрозорими — щоб читач бачив, де дата точна, а де — приблизна.

- `layout: "linear"` → проста прямокутна кімната, події на стіні по порядку.

- `layout: "thematic_clusters"` → велика зала, фізично розділена на сектори за темами. Кожен сектор має табличку з назвою теми та абзацом-описом із Етапу 5.

## Нові залежності (порівняно з оригінальним планом)

| Бібліотека | Для чого | Встановлення |
|---|---|---|
| `sentence-transformers` | Ембединги для дедуплікації та кластеризації | `pip install sentence-transformers` |
| `hdbscan` | Тематична кластеризація | `pip install hdbscan` |

Ollama залишається — але тепер використовується **тільки на Етапах 2 і 5**, де це справді потрібно.

---

## Підсумок змін

| Проблема в оригіналі | Виправлення |
|---|---|
| Злиття файлів в один потік | Чанкування всередині кожного файлу окремо |
| LLM шукає дати в сусідніх чанках — галюцинує | Детерміністичний Python-алгоритм за вже знайденими датами |
| LLM вигадує назви тем для пачок — несумісні результати | HDBSCAN-кластеризація через ембединги |
| LLM "склеює синоніми" тем — ще одне джерело помилок | Автоматичне об'єднання через центроїд кластеру |
| Немає дедуплікації | Новий Етап 3.5 через ембединги |
| Впевнені дати для всіх подій — приховані помилки | Поле `date_confidence` з рівнями точності, відображення у 3D |
